# Backend «После сделки» v0.2

FastAPI, SQLite локально / PostgreSQL в облаке, аккаунты и каталог авторских учебных ситуаций. Новые тренировки развивают навыки разговора: интересы сторон, аргументацию, реакцию на возражение и согласование следующего шага. Заранее назначенных сумм, часов, себестоимости и маржи в них нет. Сохранённые финансовые попытки работают по прежним снимкам. История подключения AI через Groq/Qwen3.8: [отчёт активации](../docs/verification/groq-live-2026-09-26.md); адаптер AI Gateway сохранён как альтернатива.

## Запуск

Из корня проекта:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8011
```

API: `http://127.0.0.1:8011/api/docs`. Vite на порту 5174 передаёт `/api` тому же backend. Сервер также отдаёт `frontend/dist`, если сборка существует до его запуска. Совместный запуск — `npm run dev` из корня.

## Слои и режимы

- `conversation_practice.py` хранит новые смысловые варианты, реакции клиента и разбор без финансового расчёта; `training.py` собирает контекст по девяти параметрам. `engine.py` управляет ходами и согласием, выбирая модель по снимку сценария. `scenarios.py` сохраняет прежние финансовые условия для совместимости.
- `dialogue.py` определяет строгий `DialogueAnalysis` и ограниченные правила demo. `responses.py` формирует ответ и разрешённые факты из намерения и серверного состояния; в generated они служат основой для формулировки AI.
- `live.py` анализирует текущую свободную реплику через совместимый Chat Completions API и предоставляет общий JSON-транспорт. Опциональный `ai_conversation.py` формулирует ответ после анализа и проверки движком; он не меняет состояние сделки.
- `feedback.py` связывает наблюдения с сохранёнными сообщениями; `repository.py` и `locking.py` отвечают за сохранение и последовательность изменений.

Demo не обращается к внешним сервисам и не претендует на понимание произвольной речи. Настройки live зависят от провайдера; шаблон — `.env.example`. Для `generic` нужны `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`. К базовому URL, например `https://provider.example/v1`, добавляется `/chat/completions`; generic-модель должна поддерживать `response_format: {"type":"json_object"}`. При отдельном запуске файл задаётся явно: `--env-file backend/.env`; корневой `npm run dev` подхватывает его автоматически.

`live_available` проверяет наличие конфигурации, а не доступность сервиса. Режим по умолчанию — demo. Для текущего Groq-подключения реальный двухшаговый ход проверен отдельно; это не гарантия доступности последующих запросов или измерение общего качества диалога.

Для текущего Groq Free заданы `LLM_PROVIDER=groq`, `GROQ_API_KEY`, явный `LLM_MODEL=qwen/qwen3.8-27b` и `LLM_REPLY_MODE=generated`. Адрес API фиксирован, Vercel OIDC не используется. Для Qwen3.8 оба шага используют строгий `json_schema` с обязательными полями и `additionalProperties:false`; `minLength`/`maxLength` проверяются локально и не передаются в Groq-схему. Для других моделей Groq используется `json_object`, совместимость проверяется отдельно. [Инструкция](../docs/Groq-бесплатное-подключение.md). Новый режим сохраняется в `Session.reply_mode` и наследуется при повторе; старые записи без поля остаются `rules`. Два AI-запроса выполняются до единственного сохранения сессии, ошибка генерации не расходует ход. Проверки текста ограниченные, не заменяют проверку качества реальных диалогов.

Пресет Vercel: `LLM_PROVIDER=vercel`, `AI_GATEWAY_API_KEY` (или `LLM_API_KEY`, затем автоматический `VERCEL_OIDC_TOKEN`) и явный `LLM_MODEL=creator/model`. URL фиксируется как `https://ai-gateway.vercel.sh/v1`; прежний `LLM_BASE_URL` игнорируется, чтобы ключ Gateway не попал к другому провайдеру. Формат — строгий `json_schema`, все четыре поля обязательны. Ошибки 401/402/403/429 очищаются от внешнего текста и объясняются пользователю. Автоматических повторов, выбора другой модели или пополнений нет. [Размещение и бесплатные лимиты](../docs/Vercel-размещение.md).

## Граница AI

`live.analyze(session, text)` возвращает `DialogueAnalysis`:

```json
{"intent":"ask_interest","evidence":"Что для вас важнее?","focus":"interest","uncertain":false}
```

Допустимы только объявленные поля и значения. `evidence` — дословная непрерывная цитата из текущей реплики длиной до 500 символов; пустая допустима лишь для `other`. Проверка структуры не доказывает правильность смысловой классификации — это отдельно проверяется на диалогах.

Провайдер получает `briefing`, `constraints`, до 12 сообщений с ролями `user`/`assistant` и текущую реплику один раз. Владелец, ID попытки, внутренние события, системные уведомления и скрытое состояние не отправляются как поля контекста. Уже произнесённые факты могут присутствовать в истории.

Новая свободная live-реплика вызывает один запрос анализа; в generated добавляется запрос формулировки ответа. Идемпотентный повтор проверяется до AI; `/proposal` и `/finish` работают без модели. Для Groq таймаут соединения — 5 секунд, остальных HTTP-фаз — 18 секунд; для generic/Vercel — 8 и 25 секунд. Ошибка провайдера, пустой ответ или невалидный JSON/анализ/реплика дают HTTP 503 без исходного текста ошибки и секретов. Реплика и ход не сохраняются; скрытого перехода в demo нет.

## Правила и обратная связь

Новые `/api/training/preview` и `/api/training/start` возвращают `Scenario.practice_model = "conversation"`, `baseline = null`, `options[].terms = null`. Вариант решения содержит `id`, `label`, `description`. Предложение сохраняет эту словесную формулировку, реакцию клиента и `terms = null`. В разборе `feedback.metrics = null`, исход — `agreement` или `no_agreement`; финансовая модель не используется ни для решения о согласии, ни для оценки навыков.

Каталог сохраняет маркер `practice_model` в новых `CaseContent`. Старое опубликованное содержимое без маркера остаётся финансовым до следующей явной публикации администратором; сохранение правок меняет только черновик. Начатые разговоры и повторы не конвертируются. `/api/scenarios` и прямой `/api/sessions` без маркера сохранены как прежний совместимый API; основной интерфейс запускает новые ситуации через training/catalog.

`/proposal` принимает `option_id` и необязательный `client_action_id`. Реакция зависит от интереса клиента, а на высокой сложности сначала требуется его выяснить. Свободная реплика не подтверждает итог сама по себе: `agreement` требует принятого варианта и отдельного завершения. Новое отклонённое предложение заменяет предыдущее принятое. Безусловная уступка может быть принята клиентом, но разбор отдельно показывает её содержание и предлагает уточнить встречный шаг; согласие не объявляется доказательством успешной тренировки.

- В новых тренировках лимит 8 / 16 / 24 хода для 5 / 10 / 15 минут; в старом API максимум 30 ходов. Учитываются свободные реплики и варианты решения. `/retry` создаёт новую попытку с теми же настройками и снимком; повтор сохранённого ключа возвращает того же ребёнка.
- Сообщения идемпотентны по `client_message_id`; другой текст с тем же ID даёт 409. Предложения и создание повторной попытки поддерживают необязательный `client_action_id`. Повтор завершения возвращает уже сохранённый результат.

Только для прежних финансовых снимков:

- `required_days = ceil(hours / daily_capacity)`, `available_hours = deadline_days × daily_capacity`, `direct_cost = hours × hourly_cost`, `contribution = price − direct_cost`.
- `feasible` учитывает срок и минимальный остаток: scope ≥0 ₽, discount ≥30 000 ₽. Остаток — **не чистая прибыль**; налоги, накладные расходы, штрафы и неопределённость отсутствуют.
- В старых финансовых сценариях при `no_agreement` API оставляет исходные метрики только для справки; интерфейс не показывает их как результат исполнения сделки. В новом разговорном формате `metrics = null` при любом исходе.

Разбор содержит `moments` с точной цитатой и `message_id`, а также три `behaviors`: выяснение потребности, аргументация, ответ на возражение. Статус `not_observed` означает отсутствие достаточного свидетельства, а не отсутствие способности. Карточка не считается аргументом; согласие клиента не считается доказательством навыка. Баллы не рассчитываются. Проверяются принадлежность цитат, порядок предложений и реакции после отказа.

`_dialogue_events` и `_proposal_events` сохраняются приватно, без выдачи клиенту. Старые активные попытки продолжаются без обязательного наличия этих полей; доступная история сохраняется, отсутствующие трактовки и решения не выдумываются. Новые поля обратной связи необязательны для ранее завершённых попыток.

## Восстановление после потери ответа

`POST /sessions/{id}/proposal` принимает `{option_id, client_action_id?}`. `POST /sessions/{id}/retry` принимает `{client_action_id?}`, пустой объект или запрос без тела. Переданный строкой `client_action_id` должен содержать 1–100 символов после удаления пробелов по краям. Отсутствующий ключ или `null` сохраняет поведение старых запросов.

Ключи `client_action_id` общие для `proposal` и `retry` внутри родительской попытки. Повтор с тем же типом действия и `option_id` для предложения возвращает сохранённый результат действия: актуальную родительскую попытку либо актуальное состояние того же ребёнка. Другой тип или пакет с тем же ключом даёт 409. Другая попытка имеет отдельное пространство ключей; `client_message_id` также использует отдельное пространство.

Проверка владельца предшествует проверке дубликата. Сохранённое предложение можно получить повторно после завершения или достижения лимита ходов, без нового хода. Ключ `/retry` работает после перезапуска и не требует повторной проверки live-конфигурации для уже созданного ребёнка. Это актуальные состояния с возможными последующими изменениями, а не кэш первоначального HTTP-ответа.

В новых сохранённых пользовательских репликах публичное поле `client_message_id` подтверждает отправку. В новом сообщении `kind:"proposal"` поле `client_action_id` появляется, если ключ был передан. Клиент может сопоставить отправку с историей после перезагрузки. Старые сообщения не дополняются идентификаторами задним числом. Приватная карта `_client_action_ids` в API не выдаётся; её отсутствие у старой попытки допустимо.

При сетевом сбое клиент повторяет исходный payload с исходным ключом до подтверждения результата. Новое осознанное действие получает новый ключ, даже если пакет тот же. Запросы без ключа совместимы со старым API, но не защищены от повторного выполнения: каждое успешное предложение расходует ход, каждый успешный `/retry` создаёт нового ребёнка.

## Сохранение и доступ

`DB_PATH` задаёт SQLite-файл; по умолчанию `backend/data/sessions.sqlite3`. Каждое сохранение атомарно. При `/retry` с ключом `Repository.save_many` сохраняет карту родителя и нового ребёнка одной транзакцией SQLite; сбой откатывает оба изменения. Отдельная процессная блокировка сериализует изменения одной попытки, включая повторы сообщений, предложений и создание повторной попытки. Разные попытки работают независимо; соединение SQLite не удерживается во время AI-запроса. Запускать **с одним worker**; нескольким процессам нужна координация в БД.

После входа история привязана к аккаунту; роли участника и администратора проверяются на сервере. Гостевая история остаётся отдельной. Анонимный токен хранится в HttpOnly cookie `posle_session_owner`, SameSite=Lax, 30 дней. Очистка этой cookie теряет доступ к гостевым записям, но не удаляет данные. [Аккаунты и администратор](../docs/Аккаунты-и-ситуации.md).

При `DATABASE_URL` используется `PostgresRepository`: JSONB, атомарный `save_many`, транзакционная advisory-блокировка одной попытки, соединение закреплено за синхронным потоком запроса. Поддерживается transaction pooler (подготовленные statements отключены); таймаут подключения 10 секунд, ожидания блокировки 10 секунд, SQL 15 секунд. Схема создаётся при первом обращении с отдельной межпроцессной блокировкой. Ошибки драйвера возвращают безопасный 503. При `VERCEL=1` без базы запуск отклоняется; Secure-cookie включается автоматически. Явный `create_app(db_path)` сохраняет изолированный SQLite-режим тестов. Локальные данные в новую базу автоматически не копируются.

До публичного размещения нужны HTTPS, ограничения запросов/расходов, политика удаления переписок и доступ к журналам. Текущий локальный запуск этого не обеспечивает.

## Проверка

```sh
.venv/bin/python -m pytest backend/tests -q
```

Тесты проверяют правила сценариев, математику, диалоговые намерения, цитаты и хронологию, совместимость старых попыток, идемпотентность, изоляцию и ошибки AI. Восстановление действий проверяется при параллельных запросах, перезапуске, конфликтующих ключах и откате транзакции создания ребёнка. HTTP-граница провайдера проверяется через `httpx.MockTransport`; реального обращения к модели нет. Это не измерение качества живой модели или обучающего эффекта продукта.

После добавления разговорной модели и исправления распознавания аргумента в свободном предложении: **749 passed, 6 skipped**. Проверены все четыре цели клиента, отказ → уточнение → аргумент → новый вариант → соглашение, обоснованное завершение без соглашения, разбор с реальными цитатами, отсутствие заданных сумм в репликах и AI-контексте, сохранение старых финансовых снимков и их повторов. Предложение с объяснением пользы учитывается как аргумент; цитаты, отрицание аргумента и карточки по-прежнему не засчитываются. Шесть пропусков относятся к отдельной тестовой PostgreSQL-базе.

При активации 26 сентября 2026: **646 passed, 4 skipped**. Пропущены отдельные PostgreSQL integration tests; это не результат тестирования PostgreSQL в текущем прогоне. Реальные ответы Groq проверены отдельно от автотестов в локальном интерфейсе (два хода) и на опубликованном сайте (свободный вопрос о бюджете и первом платеже). Публичная demo-проверка `check_deployment.py --configured` прошла 21 проверку, без AI-вызовов. Подробности — в [отчёте активации](../docs/verification/groq-live-2026-09-26.md).
