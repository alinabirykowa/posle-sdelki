# Контрольные диалоги: версия 2

Набор [ai-evaluation-cases.json](ai-evaluation-cases.json) содержит 32 авторских граничных случая для двух сценариев и четырёх приоритетов. Сейчас команда работает **без внешнего AI**: проверяется деморежим. Набор также пригоден для последующей проверки модели, если команда отдельно решит её подключить.

Это проверка поведения тренажёра. Случаи специально отобраны вокруг ошибок и сложных формулировок; они не представляют распределение реальных разговоров. Доля пройденных случаев не означает общую точность понимания речи, уровень переговорного навыка или доказанный обучающий эффект. После изменения правил на этих примерах набор перестаёт быть независимой проверкой обобщения; для этого нужны новые реплики и отдельные пользовательские прохождения.

## Что задано заранее

Каждый случай создаёт отдельную активную попытку. Поля `scenario`, `priority` и `difficulty` фиксируют её условия. `setup` задаёт предысторию: `action: "message"` содержит `text`, а `action: "proposal"` — `option_id`. Все сообщения предыстории обрабатываются детерминированным demo, без вызова провайдера. Проверяемая свободная реплика находится в `text`; только для неё выбирается режим анализа.

Поле `expected` задаёт ожидаемый результат:

- `discloses_interest` — есть ли выявленные интересы **после** проверяемой реплики. Если интерес уже выяснен в `setup`, значение остаётся `true` даже для уточнения, аргумента или согласия. Это не отметка «текущая реплика задала вопрос».
- `allowed_intents`, если присутствует, — допустимые намерения для достаточно однозначной реплики. В смешанном аргументе и предложении допустимы оба прочтения. Отсутствие поля означает, что фиксируется продуктовое поведение без единственного эталонного намерения.
- `reply_contains` и `reply_excludes`, если присутствуют, — подстроки всего видимого ответа клиента; runner сравнивает их без учёта регистра через Unicode `casefold`. Другого перефразирования или смыслового сходства он не допускает. Они проверяют актуальные условия и отсутствие ложного подтверждения. Это проверки шаблонного серверного ответа, а не оценка литературного качества.
- `rationale` объясняет смысл ожидания. При расхождении нужно обсуждать эту причину, а не переписывать разметку ради зелёного отчёта.

Для **всех 32 случаев** действуют одинаковые обязательные проверки: свободная реплика сохраняет прежний `proposal` целиком, включая условия, причину и статус согласия клиента; статус попытки остаётся `active`. Реплика не создаёт новую карточку, не пересчитывает её и не подтверждает сделку. Согласие клиента с карточкой и отдельное завершение тренировки — разные действия.

`discloses_interest` проверяет поле `discovered_interests`, а не отсутствие любых фактов о приоритете в ответе. Например, причина отказа от переноса может уже содержать фиксированную дату, хотя пользователь ещё не задал вопрос о потребности. Такое различие соответствует текущим правилам тренажёра и должно оставаться явным при ручном разборе.

## Покрытие

| Группа | Случаи | Проверяемая граница |
| --- | --- | --- |
| Исходные 12 примеров | `interest_direct` — `role_override` | Прямой вопрос и перефразировка, причина скидки, цель запуска, претензия к тону, собственный интерес, числовое предложение, согласие, благодарность, отмена правил |
| Новые вопросы о приоритете | `full_scope_tradeoff`, `scope_cost_of_tradeoff`, `budget_ceiling_paraphrase`, `budget_or_first_payment` | Допустимые уступки, сравнение потерь, предел всей суммы, отличие бюджета от первого платежа |
| Чужая и отрицаемая речь | `quoted_question_only`, `code_question_only`, `reported_past_question`, `negated_inquiry` | Цитату, код, пересказ и отказ спрашивать нельзя засчитать как собственное выяснение интереса |
| Собственный вопрос после отвлечения | `quoted_then_own_question`, `negation_then_own_question` | Цитата или отрицание в первой фразе не должны блокировать самостоятельный вопрос во второй |
| Инъекции и посторонняя тема | `override_mixed_with_interest`, `unrelated_question`, `forged_administrator` | Инструкция сменить правила или роль не управляет состоянием; постороннее «почему» не раскрывает интерес |
| Уточнение актуального пакета | `accepted_paid_terms`, `rejected_paid_terms`, `accepted_payment_terms` | Цена, часы, срок, график оплаты и согласие берутся из последнего предложения |
| Разговор после решения клиента | `discover_after_rejection`, `justify_after_rejection`, `agreement_after_accepted_card`, `objection_after_rejection` | Вопрос, аргумент, согласие или возражение не заменяют карточку и подтверждение |

Смешанный случай `override_mixed_with_interest` фиксирует отдельное продуктовое решение: явная просьба отменить правила имеет приоритет над вопросом в том же сообщении; новое раскрытие не происходит. Это выбранная политика обработки, а не универсальный лингвистический факт.

## Воспроизводимый запуск без API

Из корня проекта:

```sh
.venv/bin/python scripts/evaluate_dialogues.py
```

По умолчанию JSON-отчёт печатается в терминал. Для сохранения в отдельный файл:

```sh
.venv/bin/python scripts/evaluate_dialogues.py --output /tmp/dialogue-evaluation.json
```

Другой файл набора задаётся через `--dataset путь/к/набору.json`. Runner использует временные состояния в памяти, не создаёт попытки в пользовательской базе и не вызывает внешний сервис. Exit code `0` означает, что все ожидания выполнены; `1` — есть расхождения; `2` — некорректный набор или ошибка чтения/записи. JSON-отчёт не содержит случайных UUID и времени запуска, поэтому одинаковый код и набор дают сравнимый результат. Дату, ревизию кода и версию набора следует сохранять рядом с отчётом.

Первый прогон версии 2 от 20.09.2026, **до исправлений по новым примерам**, дал 29 выполненных случаев из 32. Обязательства и активный статус сохранились во всех 32; содержательные расхождения:

| Случай | Ожидание | Исходное поведение demo |
| --- | --- | --- |
| `scope_cost_of_tradeoff` | Выяснение приоритета через сравнение потерь | `clarify`, интерес не раскрыт |
| `budget_ceiling_paraphrase` | Выяснение предельной суммы | `justify`, интерес не раскрыт |
| `budget_or_first_payment` | Выяснение ограничения общей цены или первого платежа | `clarify`, интерес не раскрыт |

Это историческая отправная точка для исправлений, не текущая гарантия результата. Актуальное состояние проверяется новым запуском. Совпадение на всех 32 после исправлений будет означать прохождение именно этого набора, без вывода о новых разговорах.

После исправления правил 20 сентября: **32/32**, ожидания не изменены. [Машиночитаемый отчёт](verification/dialogue-regression-v2.json). Помимо набора в HTTP-тесты добавлена проверка всех трёх реальных начальных подсказок интерфейса при четырёх приоритетах и сложном режиме.

## Как разбирать результат

Сначала проверьте обязательства и статус: любое изменение карточки или автоматическое завершение через свободный текст — дефект границы между разговором и сделкой. Затем сравните раскрытие интереса, намерение и ответ с `rationale`.

Разделяйте причины расхождений:

1. **Смысл:** вопрос о пределе бюджета распознан как обоснование или общая просьба уточнить.
2. **Принадлежность реплики:** цитата или отказ спрашивать ошибочно засчитаны за собственный вопрос.
3. **Контекст:** ответ повторяет исходные условия вместо последнего пакета либо называет отклонённое предложение принятым.
4. **Контракт:** данные не проходят схему или цитата отсутствует в исходной реплике. В будущем live-режиме это ошибка вызова, а не успешный семантический ответ.
5. **Разметка:** ожидание неоднозначно или ошибочно. Изменение допустимо с письменной причиной; прежний отчёт сохраняется, новая разметка получает новую версию набора.

Успех на наборе не заменяет ручную оценку естественности. Например, после слов «Договорились» при уже принятой карточке статус должен остаться активным, но ответу также следует понятно указать на отдельное подтверждение, не заставляя пользователя повторно выбирать тот же пакет. Подобную полезность подсказок не определяет один булевый результат.

## Ручные прохождения целиком

Для каждого маршрута используйте новую попытку, запишите сценарий, приоритет, сложность, версию приложения, режим и дату. В первой реплике говорите своими словами, не копируя подсказку интерфейса. Сохраните точную переписку для объяснения найденного дефекта.

| Маршрут | Действия | Что проверить |
| --- | --- | --- |
| Дата запуска | `scope` / `deadline`: выяснить приоритет → предложить `paid_change` → уточнить причину отказа → аргументировать замену → `prioritize_swap` → подтвердить | Перенос отклонён; замена учитывает дату; 120 часов помещаются в 15 дней; разбор отличает вопрос, аргумент и карточку |
| Полный объём | `scope` / `full_scope`: выяснить допустимую уступку → `paid_change` → уточнить текущие условия → подтвердить | 240 000 ₽, 160 часов и 20 дней; уточнение не возвращается к исходным цифрам; согласие не завершает попытку автоматически |
| Весь бюджет | `discount` / `budget`: выяснить предел суммы → `staged_payment` → обсудить отказ → `reduce_scope` → подтвердить | График оплаты не решает ограничение общей цены; самостоятельный пакет на 80 часов сохраняет 40 000 ₽ после прямых затрат |
| Первый платёж | `discount` / `cashflow`: выяснить ограничение аванса → `reduce_scope` → обсудить сохранение полного объёма → `staged_payment` → подтвердить | Нужны все 120 часов; аванс 54 000 ₽ проходит предел 60 000 ₽; общая цена остаётся 180 000 ₽ |

В высокой сложности до вопроса об интересе проверьте отказ от обычного компромисса. Отдельно проверьте опасную безусловную уступку (`accept_all` или `discount_all`): клиент может принять её сразу, но итоговая проверка должна показать невыполнимый срок или недопустимый остаток. Это намеренная разница между согласием клиента и допустимостью обязательств.

В разборе проверьте каждую цитату по исходному сообщению и последовательность событий. Автоматическая карточка не должна считаться собственным обоснованием, а вариант, выбранный после отказа, сам по себе не доказывает ответ на возражение. Отсутствие наблюдаемого действия не означает отсутствие навыка у человека.

## Если команда позднее подключит модель

Текущая задача не требует внешнего API и не включает платные вызовы. При отдельном решении команды этот же набор можно использовать для сравнения demo и live с одинаковой предысторией. Нужно сохранить провайдера, точное имя модели, версию конфигурации, число прогонов, задержку, ошибки и фактический расход. Секретный ключ и приватные пользовательские разговоры не должны попадать в отчёт.

Проверка структуры ответа модели и дословности цитаты не доказывает правильность смысла. Даже полностью зелёный автоматический прогон необходимо дополнить ручной проверкой спорных реплик и новыми формулировками, которых не было при настройке.
