## Предыдущая публичная версия

Проверки ниже относятся к ранее опубликованной версии. Они не подтверждают публикацию или работу новой модели разговоров.

На публичном сайте ранее подтверждены:

- `GET /api/auth/me` возвращает `{"user":null}` для гостя.
- `GET /api/catalog` возвращает `{"items":[]}`: облачный каталог пока пуст.
- `POST /api/auth/login` с правильным Origin и неверными тестовыми данными возвращает 401. Запрос доходит до проверки логина; защита от межсайтовых запросов не блокирует корректный Origin.
- Вход с созданным аккаунтом администратора возвращает роль `admin`; `GET /api/admin/cases` отвечает 200 с пустым списком, выход завершает сессию.
- Повторный вход в браузере открывает кабинет администратора на публичном сайте.

Приватные данные публичного администратора находятся в [production-admin-access.txt](../backend/data/production-admin-access.txt), права файла — `0600`; содержимое не включается в Git или публикацию. Существующие production-секреты не скачивались. Три временные переменные начальной настройки удалены из проекта Vercel после успешного входа. Итоговый deployment опубликован без `INITIAL_ADMIN_*`; аккаунт сохранён в базе.

Эта опубликованная версия включает предупреждение о несохранённых изменениях и восстановление действий после сбоев. На момент указанных проверок публичный каталог был пуст: пример, тестовый участник и тестовый разговор в production не создавались. Полный путь «администратор → публикация → участник → разговор» был проверен локально. Локальные записи автоматически в облачную базу не переносятся.

## Создать администратора

В корне проекта откройте терминал и выполните:

```sh
.venv/bin/python scripts/create_admin.py --username your-admin --display-name "Администратор" --db-path backend/data/sessions.sqlite3
```

Команда дважды запросит пароль скрытым вводом. Требуется от 10 до 128 символов; пароль не передаётся аргументом командной строки и не выводится в результате. После создания можно войти через обычную форму или через `/#/admin`. Стандартного пароля или публичной регистрации администратора нет.

Выбор базы важен:

- `--db-path` явно выбирает локальную SQLite и имеет приоритет над `DATABASE_URL`.
- Без `--db-path` заданный `DATABASE_URL` выбирает PostgreSQL.
- Если `DATABASE_URL` не задан, используется SQLite по `DB_PATH`, а без него — `backend/data/sessions.sqlite3`.
- Скрипт читает `backend/.env`, не перезаписывая уже заданные переменные окружения.

Для администратора опубликованного сайта необходимо отдельно выполнить создание в его PostgreSQL-базе, используя настроенный `DATABASE_URL` и не указывая локальный `--db-path`. Секрет подключения хранится в окружении. Аккаунты, задания и история локальной и облачной баз разделены; копирование исходников сайта их не переносит.

Скрипт также поддерживает `--password-stdin` для защищённого канала автоматизации. Для ручной работы используйте обычный скрытый ввод.

### Начальная настройка администратора без выгрузки облачных секретов

Оператор с правом настройки сервера может создать первого администратора через три новые переменные окружения:

| Переменная | Содержимое |
| --- | --- |
| `INITIAL_ADMIN_USERNAME` | Логин первого администратора |
| `INITIAL_ADMIN_DISPLAY_NAME` | Отображаемое имя |
| `INITIAL_ADMIN_PASSWORD_HASH` | Канонический scrypt-хеш, подготовленный функцией `password_hash` из `backend/account_store.py` |

Все три значения должны быть заданы вместе; пароль в открытом виде серверной переменной не передаётся. Параметры задаёт оператор хостинга, а не посетитель страницы регистрации. После публикации сервер при запросе входа с указанным логином атомарно создаёт администратора из подготовленного хеша, если логин свободен, и затем выполняет обычную проверку пароля.

Существующего пользователя этот механизм не повышает до администратора и его пароль не сбрасывает. Существующий аккаунт администратора также остаётся без изменений. После успешного первого входа стартовые переменные следует удалить из настроек хостинга и опубликовать конфигурацию без них; сохранённый аккаунт продолжит работать в базе.

## Как задание попадает к участникам

1. Администратор создаёт ситуацию: название, короткое описание, бриф, цель, имя и компанию клиента, стартовую реплику и параметры тренировки.
2. «Сохранить» создаёт или обновляет черновик. Участникам черновик не показывается.
3. Перед публикацией администратор проверяет бриф: понятны ли ситуация, цель участника, роль клиента и правила разговора. Для новых заданий таблиц с обязательными ценами или часами нет.
4. «Опубликовать» сохраняет отдельную опубликованную версию. Она появляется в общем каталоге участников.
5. Если изменить уже опубликованное задание и сохранить его, участники продолжают видеть прежнюю опубликованную версию. Для показа правок нужно снова нажать «Опубликовать».
6. Снятие с публикации убирает задание из каталога. Архив также скрывает его; архивную запись можно отредактировать и опубликовать для восстановления.

Каждое сохранение меняет номер версии. Если два администратора одновременно редактируют одно задание, сервер отклоняет сохранение устаревшей версии с кодом 409: нужно обновить данные и сверить изменения. Повтор запроса создания с прежним идентификатором действия не создаёт дубликат.

Начатый разговор сохраняет снимок опубликованной ситуации. Последующие правки, снятие с публикации и архив не переписывают его историю и настройки. Повтор такой тренировки использует тот же снимок. Если ситуация обновилась между просмотром и новым запуском, участнику необходимо открыть актуальную версию.

Если ответ на запуск потерялся, каталог предлагает «Восстановить разговор» с прежними настройками — даже после изменения или снятия публикации. Восстановление не переключается на создание другой попытки при ошибке. Чтобы отказаться от незавершённого запуска, участник явно подтверждает «Забыть попытку».

## Что можно настроить

Ситуация содержит девять параметров `TrainingConfig`:

| Параметр | Варианты |
| --- | --- |
| Отрасль | Digital-услуги, IT и автоматизация, консалтинг |
| Тема | Дополнительные работы; скидка |
| Сложность | Обычная; сложная |
| Тон клиента | Открытый к обсуждению; сдержанный; напористый |
| Роль клиента | Руководитель проекта; владелец бизнеса; закупки |
| Цель клиента | Дата или полный объём для дополнительных работ; бюджет или первый платёж для скидки |
| Длительность | 5, 10 или 15 минут |
| Формат | Текст или голос |
| Время на ответ | Без таймера или 45 секунд |

При запуске участник отдельно выбирает demo или AI, если AI подключён. Этот режим не входит в девять параметров ситуации.

Редактор задаёт контекст разговора и учебную цель. Две доступные темы — дополнительные работы и скидка — используются как поводы для переговоров. Новые ситуации не содержат обязательной финансовой модели: участнику не нужно вводить или считать цену, часы, мощность команды и маржу.

В брифе сразу показаны ситуация, задача и собеседник. Правила доступны в закрытом блоке «Что учитывать в разговоре», чтобы быстрее перейти к началу. Участник может отвечать своими словами или использовать подсказки. Разбор относится к общению: уточнению интересов, аргументации и фиксации договорённости. Режим демо использует подготовленные ответы; AI-режим доступен при подключённом провайдере.

### Сохранённые сценарии прежней модели

У старых разговоров и опубликованных ситуаций может оставаться финансовый снимок с ценой, часами и пакетами. Он нужен для чтения прежней истории; переход на новую модель не переписывает начатые тренировки.

В старом брифе исходные числа доступны в закрытом блоке «Условия сохранённого сценария». Новые брифы этого блока не показывают. При явном сохранении старой ситуации в админке её черновик переводится в разговорный формат (`practice_model: conversation`). Предпросмотр редактора показывает этот формат. Для замены опубликованной версии администратор отдельно нажимает «Опубликовать»; до этого участники продолжают видеть прежний снимок.

## История и границы доступа

После входа разговоры привязаны к аккаунту и доступны при входе в тот же аккаунт с другого устройства в той же среде. Пользователь или администратор не может получить чужую тренировку через прямой API-запрос. Гостевая история остаётся отдельной и привязанной к анонимной cookie браузера; при входе она автоматически не переносится в аккаунт и не удаляется.

Задания общие для всех участников этой установки. Все администраторы управляют одним каталогом. Разделения по компаниям, закрытых каталогов организаций, назначения задания конкретному сотруднику и multi-tenant-изоляции пока нет.

Пароли хранятся как соль и хеш, вход использует отзывную серверную сессию и HttpOnly cookie со сроком семь дней. На Vercel cookie имеет флаг Secure. Выход отзывает текущую сессию. Публичного восстановления пароля по электронной почте пока нет.

Обычный пользователь не получает доступ к админке. Облачные проверки ограничены указанными выше запросами API; локальная опубликованная ситуация автоматически в PostgreSQL не переносилась.
